## Enhanced Implementation Plan: Deterministic TDD Act Workflow Script (Issue #133)

### 1. Wave-Based vs. Per-Task Dependency Tracking

**Analysis of the problem:**

The `topological_order` array in `lane-plan.json` is a **linear ordering** produced by `topological_sort()` in `datum/lane_plan.py` (line 126-151). It is a standard DFS-based topological sort that returns a flat list like `["task-001", "task-003", "task-002"]`. This is NOT wave-grouped. Two independent tasks (both with zero deps) might appear at positions 0 and 2 with a dependent task at position 1.

**Why BFS wave grouping is correct but the draft's approach is incomplete:**

BFS-layered scheduling (Kahn's algorithm) groups tasks into "waves" where wave N contains tasks whose dependencies all appear in waves &lt; N. This correctly identifies maximum parallelism -- tasks in the same wave have no mutual dependencies and can run concurrently.

However, there is a subtlety the draft plan misses: `pipeline-dispatch.md` defines TWO kinds of dependency:
- **Signature dependency** (satisfied by stub commit) -- unblocks downstream RED
- **Behavior dependency** (satisfied by GREEN commit) -- unblocks downstream GREEN

This means tasks in different "waves" can actually overlap their RED phases if the dependency is only behavioral. Task C (wave 2, depends on A) can start RED as soon as A's stub commit lands, without waiting for A's GREEN to complete. The wave model is too conservative for RED dispatch but correct for GREEN dispatch.

**Recommendation: Hybrid approach -- wave parallelism with fine-grained GREEN gating.**

Build BFS waves from the dependency DAG for initial dispatch ordering. Within each wave, use `parallel()` for all tasks. Between waves, the barrier from `parallel()` ensures all prior wave tasks' RED+stub is committed before downstream wave tasks begin RED. For GREEN gating, implement per-task dependency checking inside `runLane()` that polls/awaits upstream GREEN commits before starting its own GREEN.

Why NOT `pipeline()`: The `pipeline()` primitive has NO barrier between stages (item A can be in stage 3 while B is in stage 1). This means if we put tasks into a pipeline, a task with dependencies could start before its dependency finishes. There is no hook to add a gate between pipeline stages for a specific item. This makes `pipeline()` unsuitable for the dependency DAG.

**The `buildWaves()` function should:**

```js
function buildWaves(lanePlan) {
  const lanes = lanePlan.lanes;
  const inDeg = {};
  const adj = {};
  for (const [id, lane] of Object.entries(lanes)) {
    inDeg[id] = (lane.depends_on || []).length;
    for (const dep of (lane.depends_on || [])) {
      (adj[dep] = adj[dep] || []).push(id);
    }
  }
  const waves = [];
  let queue = Object.keys(inDeg).filter(id =&gt; inDeg[id] === 0);
  while (queue.length &gt; 0) {
    waves.push([...queue]);
    const next = [];
    for (const id of queue) {
      for (const child of (adj[id] || [])) {
        inDeg[child]--;
        if (inDeg[child] === 0) next.push(child);
      }
    }
    queue = next;
  }
  return waves;
}
```

**For RED specifically:** The file set is the test files derived from `lane.files` (the skeleton paths from preflight). For GREEN: only implementation files (excluding test directory). For REFACTOR: both.

### 6. Skeleton Preflight

**Yes, skeleton preflight should run before RED for each lane.** Per `references/04-act-skeleton-preflight.md` and `references/04-act.md` (line 16-20), the protocol is:

### 7. Parallel Within Wave vs. Finer-Grained Deps

**Question 8 analysis in detail:**

Consider tasks A (wave 1, no deps), B (wave 1, no deps), C (wave 2, depends on A).

With wave-based `parallel()`:
- Wave 1: `parallel([runLane(A), runLane(B)])` -- both run fully (RED-GREEN-REFACTOR) before wave 2 starts
- Wave 2: `parallel([runLane(C)])` -- C starts RED only after A AND B are completely done

This is OVERLY CONSERVATIVE. C's RED can start as soon as A's stub commit lands. C's GREEN can start as soon as A's GREEN commits. B's completion is irrelevant to C.

**However, the wave model is the simplest correct approach and matches `parallel()`'s barrier semantics.** The performance cost is that some lanes wait unnecessarily. For a typical datum epic with 5-8 tasks, the wave model adds minimal wall-clock overhead because:
1. Most tasks are independent (wave 1 is large)
2. Dependent tasks are usually in a chain (wave 2, 3 are small)

**Finer-grained tracking would require:**
- A custom event loop that monitors each lane's state
- Per-lane dependency semaphores
- Polling or callback mechanism for "upstream committed"

This complexity is not warranted for v1. The wave model is correct (never dispatches too early), maximally parallel within waves, and uses the standard `parallel()` primitive.

**Recommendation: Use wave-based parallel for v1. Note the optimization opportunity for v2.**

```js
// Deterministic TDD Act phase orchestration.
// Replaces manual RED→GREEN→REFACTOR dispatch with a mechanical
// Workflow script that enforces gates, file ownership, and dependency order.

// Invocation:
//   /workflow datum-tdd-act --run-id &lt;ID&gt; --epic-branch &lt;BRANCH&gt; --lane-plan-path .datum/lane-plan.json

  name: 'datum-tdd-act',
  description: 'Deterministic TDD Act phase: RED→GREEN→REFACTOR per lane with dependency gating',
  version: '1.0.0',

// ── Schema Definitions ──────────────────────────────────────────────────

const LanePlanSchema = {
  schema_version: 'string',
  total_lanes: 'number',
  topological_order: ['string'],
  file_ownership: 'object',
  lanes: 'object',
};

const StageVerifySchema = {
  verified: 'boolean',
  error: 'string?',
  exit_code: 'number?',
};

const FailureRecord = {
  task_id: 'string',
  stage: 'string',   // RED | GREEN | REFACTOR
  attempt: 'number',
  error: 'string',

// ── Configuration ──────────────────────────────────────────────────────

  standard: 'sonnet',
  reasoning: 'opus',

// ── Helpers ──────────────────────────────────────────────────────────────

function buildWaves(lanePlan) {
  const lanes = lanePlan.lanes;
  const ids = Object.keys(lanes);
  const inDeg = {};
  const adj = {};

  for (const id of ids) {
    const deps = lanes[id].depends_on || [];
    inDeg[id] = deps.length;
    for (const dep of deps) {
      (adj[dep] = adj[dep] || []).push(id);
    }
  }

  const waves = [];
  let queue = ids.filter(id =&gt; inDeg[id] === 0);

  while (queue.length &gt; 0) {
    waves.push([...queue]);
    const next = [];
    for (const id of queue) {
      for (const child of (adj[id] || [])) {
        inDeg[child]--;
        if (inDeg[child] === 0) next.push(child);
      }
    }
    queue = next;
  }

  return waves;
}

// ── Per-Lane TDD Execution ──────────────────────────────────────────────

async function runLane(taskId, lanePlan, worktreePaths, runId, testCommand, language) {
  const lane = lanePlan.lanes[taskId];
  const worktreePath = worktreePaths[taskId];
  const isStructural = lane.stage === 'structural';

  log(`[${taskId}] Starting lane: ${lane.title} (${isStructural ? 'structural' : 'behavioral'})`);

  if (isStructural) {
    // Structural tasks bypass RED and GREEN — REFACTOR only
    const refactorResult = await runRefactor(taskId, lane, worktreePath, runId, testCommand);
    if (!refactorResult) {
      appendFailure(runId, taskId, 'REFACTOR', 'Refactor failed for structural task');
      return null;
    }
    log(`[${taskId}] Structural lane complete`);
    return { taskId, status: 'completed' };
  }

  // ── Skeleton Preflight ──────────────────────────────────────────────
  const preflight = await agent(
    `Run this command and return the full JSON output:
cd ${worktreePath} &amp;&amp; datum skeleton --task-id ${taskId} --language ${language} --tasks .datum/lane-plan.json --output .datum/runs/${runId}/preflight-${taskId}.json
Then read and return the contents of .datum/runs/${runId}/preflight-${taskId}.json`,
    { model: MODEL.fast }
  );

  // ── RED ──────────────────────────────────────────────────────────────
  log(`[${taskId}] RED: writing failing tests`);

  const redResult = await agent(
    buildRedPrompt(taskId, lane, worktreePath, preflight, runId, testCommand),
    { model: MODEL.standard }
  );

  // Verify RED: tests must FAIL
  const redVerify = await agent(
    `cd ${worktreePath} &amp;&amp; datum verify-stage red --test-command "${testCommand}"
Report the result as JSON: {"verified": true/false, "error": "...if failed"}`,
    { model: MODEL.fast, schema: StageVerifySchema }
  );

  if (!redVerify.verified) {
    log(`[${taskId}] RED verification FAILED: ${redVerify.error}`);
    appendFailure(runId, taskId, 'RED', redVerify.error || 'Green blindness — tests passed at RED');
    return null;
  }

  log(`[${taskId}] RED verified — tests correctly failing`);

  // ── GREEN ─────────────────────────────────────────────────────────────
  log(`[${taskId}] GREEN: making tests pass`);

  // Get test signal for GREEN brief (redacted — no test source)
  const testSignal = await agent(
    `cd ${worktreePath} &amp;&amp; datum test-signal --framework pytest --input &lt;(cd ${worktreePath} &amp;&amp; ${testCommand} 2&gt;&amp;1 || true)
Return the JSON output only.`,
    { model: MODEL.fast }
  );

  const greenResult = await agent(
    buildGreenPrompt(taskId, lane, worktreePath, testSignal, runId, testCommand),
    { model: MODEL.standard }
  );

  // Verify GREEN: tests must PASS
  const greenVerify = await agent(
    `cd ${worktreePath} &amp;&amp; datum verify-stage green --test-command "${testCommand}"
Report the result as JSON: {"verified": true/false, "error": "...if failed"}`,
    { model: MODEL.fast, schema: StageVerifySchema }
  );

  if (!greenVerify.verified) {
    log(`[${taskId}] GREEN verification FAILED: ${greenVerify.error}`);
    appendFailure(runId, taskId, 'GREEN', greenVerify.error || 'Tests still failing after GREEN');
    return null;
  }

  log(`[${taskId}] GREEN verified — tests passing`);

  // ── REFACTOR ──────────────────────────────────────────────────────────
  const refactorResult = await runRefactor(taskId, lane, worktreePath, runId, testCommand);
  if (!refactorResult) {
    appendFailure(runId, taskId, 'REFACTOR', 'Refactor failed');
    return null;
  }

  log(`[${taskId}] Lane complete`);
  return { taskId, status: 'completed' };
}

async function runRefactor(taskId, lane, worktreePath, runId, testCommand) {
  log(`[${taskId}] REFACTOR: cleanup + full AC coverage`);

  const refactorResult = await agent(
    buildRefactorPrompt(taskId, lane, worktreePath, runId, testCommand),
    { model: MODEL.standard }
  );

  // Verify REFACTOR: tests must still PASS
  const refactorVerify = await agent(
    `cd ${worktreePath} &amp;&amp; datum verify-stage green --test-command "${testCommand}"
Report the result as JSON: {"verified": true/false, "error": "...if failed"}`,
    { model: MODEL.fast, schema: StageVerifySchema }
  );

  if (!refactorVerify.verified) {
    log(`[${taskId}] REFACTOR verification FAILED: ${refactorVerify.error}`);
    return null;
  }

  return refactorVerify;
}

  const record = JSON.stringify({
    task_id: taskId,
    stage,
    error,
    timestamp: new Date().toISOString(),
  });
  log(`FAILURE: ${record}`);

}

// ── Main Workflow ────────────────────────────────────────────────────────

export default async function run(args) {
  const runId = args.runId || new Date().toISOString().replace(/[:.]/g, '-').slice(0, 19);
  const epicBranch = args.epicBranch;
  const lanePlanPath = args.lanePlanPath || '.datum/lane-plan.json';
  const testCommand = args.testCommand || 'pytest -q';
  const language = args.language || 'python';

  // ── Phase: Topology ──────────────────────────────────────────────────
  phase('Topology');

  const lanePlan = await agent(
    `Read the file at ${lanePlanPath} and return its contents as a JSON object.`,
    { model: MODEL.fast, schema: LanePlanSchema }
  );

  const waves = buildWaves(lanePlan);
  log(`Topology: ${lanePlan.total_lanes} lanes in ${waves.length} waves`);
  for (let i = 0; i &lt; waves.length; i++) {
    log(`  Wave ${i}: [${waves[i].join(', ')}]`);
  }

  // ── Phase: Setup ──────────────────────────────────────────────────────
  phase('Setup');

  const laneIds = Object.keys(lanePlan.lanes);
  const setupResult = await agent(
    `Run this command and return the output:
datum worktrees setup --run-id ${runId} --epic-branch ${epicBranch} --lane-ids ${laneIds.join(',')}
Return the JSON mapping of lane_id to worktree_path.`,
    { model: MODEL.fast }
  );

  // Parse worktree paths from setup output
  const worktreePaths = setupResult; // agent returns parsed JSON

  // ── Phase: Act ────────────────────────────────────────────────────────
  phase('Act');

  const results = {};
  const failures = [];

  for (let waveIdx = 0; waveIdx &lt; waves.length; waveIdx++) {
    const wave = waves[waveIdx];
    log(`=== Wave ${waveIdx} starting: [${wave.join(', ')}] ===`);

    const waveResults = await parallel(
      wave.map(taskId =&gt; async () =&gt; {
        try {
          return await runLane(taskId, lanePlan, worktreePaths, runId, testCommand, language);
        } catch (err) {
          log(`[${taskId}] FATAL ERROR: ${err.message}`);
          appendFailure(runId, taskId, 'UNKNOWN', err.message);
          return null;
        }
      })
    );

    for (let i = 0; i &lt; wave.length; i++) {
      results[wave[i]] = waveResults[i];
      if (!waveResults[i]) {
        failures.push(wave[i]);
      }
    }

    log(`=== Wave ${waveIdx} complete: ${wave.length - failures.filter(f =&gt; wave.includes(f)).length}/${wave.length} succeeded ===`);
  }

  // ── Phase: Merge ──────────────────────────────────────────────────────
  phase('Merge');

  const completedLanes = Object.entries(results)
    .filter(([_, r]) =&gt; r?.status === 'completed')
    .map(([id]) =&gt; id);

  if (completedLanes.length === 0) {
    log('No lanes completed — skipping merge');
  } else {
    // Merge in topological order (only completed lanes)
    const mergeOrder = lanePlan.topological_order
      .map(item =&gt; typeof item === 'string' ? item : item.root)
      .filter(id =&gt; completedLanes.includes(id));

    await agent(
      `Run this command:
datum worktrees merge --epic-branch ${epicBranch} --lane-order ${mergeOrder.join(',')} --commit-message "act: merge ${completedLanes.length} lanes for ${epicBranch}"`,
      { model: MODEL.fast }
    );

    log(`Merged ${completedLanes.length} lanes in order: [${mergeOrder.join(', ')}]`);
  }

  // ── Phase: Cleanup ────────────────────────────────────────────────────
  phase('Cleanup');

  await agent(
    `Run this command:
datum worktrees cleanup --run-id ${runId} --epic-branch ${epicBranch}`,
    { model: MODEL.fast }
  );

  // Write failure records
  if (failures.length &gt; 0) {
    await agent(
      `Write the following failure records to .datum/runs/${runId}/act-failures.jsonl:
${failures.map(id =&gt; JSON.stringify({ task_id: id, stage: results[id]?.stage || 'UNKNOWN', error: results[id]?.error || 'Lane failed' })).join('\n')}`,
      { model: MODEL.fast }
    );
  }

  // ── Summary ──────────────────────────────────────────────────────────
  log(`\nAct phase complete:`);
  log(`  Total lanes: ${lanePlan.total_lanes}`);
  log(`  Completed: ${completedLanes.length}`);
  log(`  Failed: ${failures.length}`);
  if (failures.length &gt; 0) {
    log(`  Failed lanes: [${failures.join(', ')}]`);
  }

  return {
    runId,
    total: lanePlan.total_lanes,
    completed: completedLanes.length,
    failed: failures.length,
    failedLanes: failures,
  };
}
```

```python
@app.command(name="verify-stage")
def verify_stage_cmd(
    stage: str = typer.Argument(..., help="Stage to verify: 'red', 'green', or 'baseline'"),
    repo_path: str = typer.Option(".", "--repo", help="Repository root path"),
    test_command: str = typer.Option("pytest -q", "--test-command", help="Test runner command"),
):
    """Verify TDD stage gate.

    red:      Tests must FAIL (green blindness check). Exit 0 if failing, exit 1 if passing.
    green:    Tests must PASS. Exit 0 if passing, exit 1 if failing.
    baseline: Tests must PASS before starting a new RED cycle. Exit 0 if passing, exit 1 if failing.
    """
    import shlex
    from datum.tdd_driver import (
        DirtyBaselineError,
        GreenBlindnessError,
        verify_green_baseline,
        verify_red_stage,
    )

    cmd = shlex.split(test_command)
    path = Path(repo_path).resolve()

    try:
        if stage == "red":
            verify_red_stage(path, test_command=cmd)
            console.print("[green]RED verified: tests are correctly failing.[/green]")
        elif stage in ("green", "baseline"):
            verify_green_baseline(path, test_command=cmd)
            console.print("[green]GREEN verified: tests are passing.[/green]")
        else:
            console.print(f"[red]Unknown stage: {stage}. Use 'red', 'green', or 'baseline'.[/red]")
            raise typer.Exit(1)
    except GreenBlindnessError as e:
        console.print(f"[red]RED verification FAILED: {e}[/red]")
        raise typer.Exit(1)
    except DirtyBaselineError as e:
        console.print(f"[red]Baseline verification FAILED: {e}[/red]")
        raise typer.Exit(1)
```

### Gaps and Concerns for the Implementer

1. **FleetView API uncertainty.** The `agent()`, `parallel()`, `phase()`, `log()` primitives are described in the system facts but there is no reference implementation or API documentation in the repo. The implementer should verify:
   - Whether `agent()` supports `cwd:` as an option (critical for worktree isolation)
   - Whether `agent()` supports `schema:` for structured output
   - Whether `parallel()` returns results in order or as a map
   - Whether there is a way to pass environment variables to agents

2. **Test signal generation for GREEN.** The GREEN agent needs a redacted test signal. The workflow uses `datum test-signal` but the exact invocation pattern (piping test output) needs to match the existing test_signal.py expectations. The test_signal module reads from a file or stdin -- verify the correct invocation.

3. **Commit queue integration.** The existing `pipeline-dispatch.md` describes a commit queue (`datum commit-queue`) for serializing commits. The worktree model (each lane has its own branch) eliminates the commit queue's primary purpose (preventing concurrent writes to the same branch). However, the merge phase still needs serialization. The implementer should decide: keep the commit queue for merge, or rely on `merge_lane_branches()` which already serializes merges.

4. **Retry logic is NOT in v1 scope.** The draft plan does not include the retry ladder (standard -&gt; reasoning -&gt; reasoning+verbose) from `references/model-tiers.md`. Each stage gets one attempt. Retry should be a v2 enhancement. The failure is recorded and the lane is skipped.

5. **Adversarial agent is NOT in v1 scope.** Per `references/04-act.md`, an ADVERSARIAL agent runs after REFACTOR. This is not in the draft plan and should be deferred to v2.

6. **Security and docs sidecars are NOT in v1 scope.** The Act phase doc mentions `security-sidecar` and `docs-scaffolder` running alongside the main loop. These are deferred.

7. **`topological_order` items are `TopologicalOrderItem` (RootModel), not plain strings.** When reading from `lane-plan.json`, the items are strings. But when using the Pydantic schema, they are wrapped in `TopologicalOrderItem.root`. The workflow reads raw JSON, so this is fine -- but the merge-order filtering line must handle this:
   ```js
   const mergeOrder = lanePlan.topological_order
     .map(item =&gt; typeof item === 'string' ? item : item.root)
   ```

8. **File ownership enforcement is prompt-only in v1.** There is no mechanical post-commit check in the workflow. The test_ratchet pre-commit hook catches some violations, but general file-ownership enforcement relies on the agent following instructions. The implementer should add a post-commit `git diff --name-only` check and fail the lane if non-owned files are touched.

9. **install.sh symlink.** The workflow file lives at `skills/datum-tdd-act.js` in the repo. For Claude Code to discover it, it needs to be symlinked to `~/.claude/workflows/datum-tdd-act.js`. The `install.sh` script's `register_tool` function creates symlinks to `~/.claude/skills/datum`, but workflows live in a different directory. A new registration step is needed in `install.sh`.

10. **No `datum act-red` / `datum act-green` CLI commands exist.** The agents are prompted directly with full briefs. There is no thin CLI wrapper for running a specific TDD stage. The workflow constructs the full brief in JS and passes it as the agent prompt. This is the correct approach -- adding CLI wrappers would create unnecessary indirection.
