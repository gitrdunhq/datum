# Shared Alignment Library Extraction Plan (Issue #186)

## Executive Summary

DTW-alignment code (DER, SentenceAligner, DTW, ConversationFormatter, and related files) is manually triplicated across RecordPro, ProofHarness, and ProofHarnessWindows with a mix of identical copies, cosmetic divergences, and genuine semantic differences. The pure algorithmic files (DTW, DER, SentenceAligner) depend only on `Domain` + `Foundation` + `NaturalLanguage` and are extractable into a shared library target within `Record-CrossPlatform-Foundation`, which already hosts both the cross-platform Domain types and the Windows harness. The harness-orchestration files (PipelineRunner, ResultPrinter, Compare, Terminal) are NOT extractable because they diverge semantically and import platform-specific infrastructure (`AudioInfrastructure`, `MLInfrastructure`, `XGrammarSummarizationPlugin`, `InferenceTelemetry`) that would drag heavy macOS-only dependencies into the shared library. The `NaturalLanguage` framework used by `SentenceAligner.splitSentences()` is Apple-only and requires a `#if canImport(NaturalLanguage)` guard with a regex-based fallback for Windows.

## Recommended Home for the Shared Target

### Recommendation: New target `Alignment` in `Record-CrossPlatform-Foundation`

**Rationale**:
1. `Record-CrossPlatform-Foundation` already hosts the cross-platform `Domain` target that the alignment code depends on. Adding an `Alignment` target is a natural extension of its purpose.
2. It already has a `Package.swift` with `swift-tools-version:6.2` and strict concurrency. The Windows harness (`ProofHarnessWindows`) is already a target in this package, so the dependency is trivial: just add `"Alignment"` to its deps array.
3. For ProofHarness (standalone macOS CLI in `Tools/ProofHarness/`), it can add a path-based dependency: `.package(path: "../../Record-CrossPlatform-Foundation")` and import the `Alignment` product.
4. For RecordPro (target in root `Package.swift`), it already depends on `Record-Foundation` for `Domain`. Adding a dependency on `Record-CrossPlatform-Foundation` for `Alignment` is straightforward since `Record-CrossPlatform-Foundation` is a local sub-package.
5. Per AGENTS.md layer rules, the alignment algorithms are pure Domain-layer code (Foundation only, no Infrastructure). Housing them in the cross-platform foundation package is architecturally correct.

### Rejected alternatives

- **(b) New top-level package `Record-Alignment`**: Creates a new Package.swift just for 4 files (~310 LOC). Excessive ceremony; the monorepo already has enough sub-packages.
- **(c) Target inside RecordPro**: RecordPro depends on `MLX`, `MLXLMCommon`, `AudioInfrastructure`, `MLInfrastructure` -- all macOS-only. Adding a target here that Windows needs would either require stripping RecordPro's deps or creating a parallel package graph. Defeats the purpose.
- **(d) Target inside Record-Foundation**: Record-Foundation is used by everyone, but alignment is not foundational -- it is a functional concern that belongs above Domain. Adding it to Record-Foundation would violate the narrow responsibility of that package.

## Risks and Mitigations

| Risk | Severity | Mitigation |
|------|----------|------------|
| **NaturalLanguage unavailable on Windows** | HIGH | `SentenceAligner.splitSentences()` uses `NLTokenizer(unit: .sentence)`. Wrap in `#if canImport(NaturalLanguage)` with a fallback that splits on sentence-ending punctuation (`.`, `?`, `!`) followed by whitespace. The fallback is less linguistically accurate but functional. |
| **No Windows CI** | MEDIUM | The CI config at `.github/workflows/ci.yml` is entirely commented out. There is no CI for any platform, let alone Windows. The `ProofHarnessWindows` target has never been CI-validated. Mitigation: ensure `swift build --target ProofHarnessWindows` succeeds locally in `Record-CrossPlatform-Foundation`. File a follow-up issue to enable CI. |
| **Two Domain packages** | LOW | `Record-Foundation/Sources/Domain` and `Record-CrossPlatform-Foundation/Sources/Domain` are currently identical (DiarizedTranscript.swift diff is empty). The shared Alignment target depends on the cross-platform Domain. RecordPro depends on Record-Foundation's Domain. Since both define the same types with the same names, there will be a type identity conflict if a consumer imports both `Domain` modules. Mitigation: the root Package.swift already resolves `Domain` from `Record-Foundation`; the `Alignment` product from `Record-CrossPlatform-Foundation` must be compiled against the same `Domain`. This requires Record-CrossPlatform-Foundation to use `Record-Foundation`'s Domain (via path dependency) rather than its own copy. **This is the single hardest technical challenge**: either (a) Record-CrossPlatform-Foundation adds `.package(path: "../Record-Foundation")` and removes its local Domain target, or (b) the Alignment target is defined with an explicit `Domain` dependency that the root Package.swift resolves. Option (a) is cleaner but breaks the cross-platform standalone build (Record-Foundation may have macOS-only deps). Needs investigation. |
| **SentenceAligner behavior change in RecordPro** | LOW | RecordPro previously returned `[]` when `rawDuration &lt;= 0`. The shared version estimates duration from speaker end-times. This is more robust but a behavior change. Mitigation: document in PR. The old behavior was arguably a bug (silent data loss). |
| **DTW tie-breaking change** | VERY LOW | RecordPro used exact floating-point equality (`==`) for tie-breaking; the shared version uses `&lt;=`. In practice, DTW costs are sums of `abs()` values and ties are vanishingly rare. Existing DTWWordAlignerTests will validate. |
| **Concurrent agent edits** | LOW | Other agents are refactoring PipelineRunner/ResultPrinter/DER/SentenceAligner for cyclomatic complexity. This plan runs AFTER their commit. If their refactor changes the function signatures of the extractable files, the shared library versions must be updated to match. |
