**What to audit for Phase 2:**
1. The existing `UITheme` enum (Domain/Config/UITheme.swift) — only has `.classic` and `.broadsheet` cases, no rich theming data
2. The existing `AppConfig.uiTheme` field — stores theme selection, not theme data
3. The existing theme switching mechanism via `NotificationCenter.themeChanged` in App.swift
4. The existing SwiftUI Environment injection pattern (`textScale` in BroadsheetRootView) — this is the pattern to extend
5. The existing `Color` extension system (DesignTokens.swift) — 15+ colors defined as static properties
6. How the theme switch currently works: `AppContentView` does a `switch appState.settings.uiTheme` and renders either `BroadsheetRootView` or `MainWindowView`
7. The `SettingsViewModel.uiTheme` property and how it proxies to `AppState.settings.uiTheme`
8. The `BroadsheetAppState` class — check what theming-related state it holds
9. Existing hardcoded colors across all views — count how many Color.xxx references exist vs what could be themeable
10. What an `AppTheme` protocol should expose: colors, fonts, metrics, spacing, corner radii, etc.

### Phase 3: JSON Skinning Engine
Tasks:
- **3.1.1**: Define `theme-schema.json`
- **3.2.1**: Implement `JSONTheme` and `ThemeLoader`

**What to audit for Phase 3:**
1. Existing JSON parsing patterns in the codebase (e.g., JSONSpeakerProfileStore, AppConfig Codable)
2. File I/O patterns for loading theme files from disk
3. What the JSON schema should look like: colors (hex strings), fonts (size/weight/design), metrics (numbers), etc.
4. Where theme JSON files should be stored (bundle? user documents? both?)
5. How `ThemeLoader` should integrate with the `AppTheme` protocol
6. How to handle fallback to built-in `BroadsheetTheme` when JSON fails to load
