## Verdict: DROP-IN (mechanically) — but NOT an accuracy win on this fixture

**Integration lift: trivial.** The swap is ~15 changed lines in one file:
- `OfflineDiarizerManager` returns the **same** `DiarizationResult`/`TimedSpeakerSegment` types as the streaming `DiarizerManager`, so segment extraction code is unchanged.
- API deltas: `init(config: OfflineDiarizerConfig)` + `prepareModels()` (self-downloading, replaces `DiarizerModels.downloadIfNeeded()` + `initialize(models:)`); entry point is `process(audio: [Float]) async throws` (async, vs the sync `performCompleteDiarization`) — slots straight into the existing `runDetached` closure.
- Models: different variant ("offline", pyannote community-1) in the same HF repo `FluidInference/speaker-diarization` — **34 MB**, auto-downloaded in ~10s on first `prepareModels()`. Cached at `~/Library/Application Support/FluidAudio/Models/`.
- Concurrency: same story as streaming — non-Sendable class (uses `nonisolated(unsafe)` internally, spawns its own detached tasks); the plugin's existing `nonisolated(unsafe)` escape works unchanged. macOS 14+ requirement — fine (repo targets macOS 15).
- Shipping-code cleanup needed: map `OfflineDiarizationError` (new error enum, incl. `.noSpeechDetected`) — currently falls through to generic `inferenceFailed`.

## Key findings / blockers

1. **Default offline config under-clusters badly**: VBx warm-starts with 15 AHC clusters, then collapses to **2** — FEO070+FEO072+MEE071 all merge into one 622s cluster. Worse than streaming on every metric.
2. **numSpeakers=4 hint** recovers 4 clusters and beats streaming on purity (68.1 vs 66.4) but is slightly worse on DER, still merges FEO070/FEO072 into one cluster, and **splits MEE071 across two clusters (best-cluster 40.1% vs 72.2% streaming) — violates the MEE071 must-not-regress guard**. And production doesn't know the speaker count a priori.
3. **Both engines share the same dominant confusion** (FEO070/FEO072 merge; conf 27-44%, DER 43-56% vs upstream's 17.7% AMI claim). Also suspicious: the RTTM's total reference speech (901.3s) equals the full audio duration (901s) — near-100% speech density, and the offline segmenter measured 88.7% speech ratio. Suggests the fixture (audio and/or RTTM) is the limiting factor, not the clustering engine — worth verifying against the known tap time-stretch issue before drawing engine conclusions.
4. Ops notes: first-run model download 34 MB / ~12s prepare; warm prepare 0.1-0.5s; memory unremarkable; macOS 14+ only; `process()` spawns its own detached tasks (segmentation ∥ embedding) — no thread-safety issues observed under the plugin's existing isolation pattern.

**Bottom line**: swapping engines is cheap (an afternoon including error-mapping polish), but on this fixture it does not fix the accuracy problem and regresses MEE071 under the 4-speaker hint. Don't ship on this evidence — investigate the fixture/audio quality signal first.</result>
