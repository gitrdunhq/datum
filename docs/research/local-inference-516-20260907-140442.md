# Local inference for datum stage agents (#516, #515) — measured plan

run_id: 20260907-140442 · audit_dir: `.temp/local-516/` (70 request/response pairs, `requests.jsonl` index, `props-qwen38.json`, run logs) · endpoint: llama.cpp b10448 behind llama-swap at `http://192.168.0.211:8080/v1` · models probed: qwen38 (Qwen3.8-27B UD-Q5_K_M + MTP), qwopus9b (Qwopus3.5-9B-Coder Q6_K + MTP), qwen (Qwen3.6-35B-A3B UD-Q4_K_M, no speculative decoding, `--reasoning off`, -c 32768) · metric: wall-clock, not cost. ## 0. Load-bearing findings

1. **Model speeds, same small task, single stream:** qwopus9b decodes 100–108 tok/s with prefill 970–1740 tok/s; qwen (35B-A3B) 72–75 tok/s, prefill 700–1570; qwen38 30–38 tok/s, prefill 530–570. Time to first token on a 415-token uncached prompt: 0.41 s / 1.1 s (first call after load, 0.7 s after) / 1.6 s. qwopus9b is the fastest at everything measured.
2. **Residency and swaps:** two llama-swap groups. qwopus9b sits in a persistent coder group (port 5808) and was never evicted; the main group (port 5807) holds one of qwen38/qwen/… and swaps on request: my probe 1 (asking for qwen38 while `qwen` was resident) cost 25.7 s, the qwen batch cost 28.4 s to swap in, restoring qwen38 cost 25.3 s. Split routing between qwopus9b and one main-group model costs no swap; alternating two main-group models costs ~25 s each time.
3. **KV cache, level 1 (automatic):** byte-identical repeats and conversation continuations hit on all three models (411/415, 498/502, 873/877 on repeats; 776/810, 843/901 on tool-loop turns), and a different-prefix request in between did not evict (411/415 again afterwards on all three). Partial-prefix reuse (same preamble, different tail) is unreliable: 19 to 870 cached tokens against a 411-token shared preamble in nine samples. Design for identical bytes and continuations.
4. **Reasoning controls:** on qwen38 the chat template prepends a "Reasoning effort is set to …" sentence to the system message, so each effort value is a different prefix (426/450/462 prompt tokens for none/low/high, cache 0 on each change); `none` gives zero reasoning and is honoured. On qwen, `reasoning_effort` is inert under `--reasoning off` (426 tokens, no reasoning, cache hit across none/high/absent) — a swap to `qwen-think` would be needed to test thinking there. On qwopus9b thinking is on by default and a 120-token cap returns empty content (`finish_reason: length`); `chat_template_kwargs.enable_thinking=false` fixes it.
5. **Schema output:** `response_format: json_schema` strict 3/3 on all three models, `json_object` 1/1 on all three, forced `submit_answer` tool 3/3 on all three. Every path drops optional fields (`read_witness` missing in 7 of 9 json_schema answers, `files_written` in 6 of 9): anything a runner reads must be in `required`. The grammar path costs ~25% decode on qwen38 and qwopus9b.
6. **Tool calling:** native `tool_calls` with `finish_reason: "tool_calls"`, two turns deep on qwen38 and qwopus9b, with continuation caching (776/810). The empty-content-after-tool-result quirk did not reproduce (0/2). qwopus9b guessed `datum test` right after reading a config that said `uv run pytest -x -q`.
7. **Concurrency:** qwen38 (`--parallel 1`): the second of two simultaneous requests never returned within 300 s, no error. qwopus9b (single slot): the second queued and both finished in 1.08 s total. qwen (several slots): two ran truly in parallel with per-request decode 26 tok/s each (from 75); three ran at 17–26 each. Aggregate decode fell from 75 to 52 (two) and 66 (three) tok/s, so parallel slots lose throughput and, worse, land requests on slots without the prefix (one of three got cache 0). Serialize on every model; a client cap of 1 per server process is the design, not an optimisation.
8. **Context cost:** an uncached 20k-token prompt takes 14.3 s on qwopus9b, 13.1 s on qwen, 40.2 s on qwen38; decode at 20k context drops to 76 / 41 / 24 tok/s (from 105 / 75 / 33). qwen's ceiling is 32768. Every uncached kilotoken is ~0.8 s on the two fast models and ~1.9 s on qwen38.
9. **Context-reduction tools:** headroom refuses to compress code (`router:protected:recent_code`, 0% on a 7.2 KB Python file) and is lossy on text (a 12-commit `git log --stat` went 3244 → 1508 tokens but five commit headers vanished from the compressed view; `headroom_retrieve` with the sha found the right chunk). tokensave's map/signatures/body views are 66–84% smaller than a raw read of the same file, but bare-name `tokensave_body` returned the wrong bytes twice because the graph was indexed on `main` while the checkout is another branch; the qualified name was right. Under datum, tokensave needs a per-worktree index and headroom stays off for code and relayed files.
10. **Wiring:** `datum/agent_loop.py` has no production caller, nothing in the repo reads the `runtime` block of `.datum/config.json`, and the Workflow sandbox has no sockets, so the only route to the endpoint today is a hosted datum-cli runner executing a `datum local-stage` bridge as a batch step (mechanism A, §3).

## 3. Call inventory — what can move to the local endpoint, and by which mechanism

Every LLM call in the pipeline is `agent(prompt, opts)` inside a Workflow script in the host's sandbox, dispatched as a Claude Code subagent chosen by `stageOpts(kind)`. The sandbox has no filesystem or sockets, so a script cannot reach llama.cpp itself. Two routes:

- **Mechanism A — bridge step (recommended first).** The stage becomes a deterministic batch step: a hosted `datum-cli` runner executes `datum local-stage <kind> --packet <file> --out <file>` and the script reads a receipt (path, bytes, sha), like the lane-spec export. datum's Python loop calls the endpoint with native tool calls, executes tools in-process under `command_guard` (git is read-only there, so the commit is a following batch step), and emits the stage schema via `submit_answer`. Cost per stage: one hosted Haiku runner call as transport and the Bash tool's 600 s ceiling on the whole local stage.
- **Mechanism B — host routing.** The host's OpenAI-compatible workflow mode, the apparent consumer of the `runtime` block in `.datum/config.json` (no reader in this repo; the block still points at oMLX port 12201). If honoured, every `agent()` goes local including the batch runners, and `agent_types` must be false, which also disables the PreToolUse hooks and revives the LLM ownership checks. **Unverified** end to end.

## 4. Per-stage model routing and the lane wall-clock model

**Recommendation: qwopus9b for every local stage, qwen38 (or hosted balanced) only as the named-failure escalation.** It is the fastest at prefill and decode, always resident, single-slot (so it queues instead of parallel-thrashing), and passes every mechanism probe. Its measured weakness is judgement (the guessed `datum test`), and the deterministic batch verifiers, not a stronger model, are the mitigation datum already has. qwen (35B-A3B) is close on prefill but 30% slower on decode, loses more at long context, has no thinking without a swap to `qwen-think`, and its multiple slots are a liability (§5). qwen38 is 3x slower and only earns its place where reasoning matters (contract lens, GREEN retry after a named failure).

## 5. Concurrency design

- **Client cap of 1 per server process**, enforced where requests originate: `datum local-stage` takes an exclusive `flock` on `.datum/local/<model>.lock` around each HTTP request (lanes are separate runner processes). With qwopus9b as the only local model this is one global lock; `local.max_concurrency` stays a config knob (1 default) for a future second server process.
- **Queue, never parallel.** qwen38 hung the second request for 300 s (E6); qwen served it in parallel at a third of the speed and off-cache. Both are worse than waiting.
- **Timeouts.** Connect 60 s; read `max(120, prompt_tokens / 800 + max_tokens / 60 + 30)` s for qwopus9b (halve the rates for qwen38); a hung request is `local_request_timeout`, retried once only if the worktree dirty guard says nothing was written.
- **Act's five lanes stay five.** Worktrees, hosted batches and test suites run in parallel; only the inference requests serialize behind the lock, which overlaps lane A's tests with lane B's decode. Do not reduce the batch size.
- **Queue order.** FIFO with the lock held per request, not per stage; measure the cache hit share before adding a "same stage kind first" priority.
- **Bash ceiling.** A local stage under mechanism A cannot exceed 600 s of runner time; `max_steps` 10 for writers; exhaustion is `local_stage_budget_exhausted`.
- **Residency.** `GET /running` before every request; a request to a non-resident model logs `local_model_swap` with the first-request wall. With qwopus9b only, zero swaps is the expected steady state.

## 6. Prompt-shape recommendations

- **Byte-stable prefix per (model, stage kind):** the server's reasoning sentence (qwen38 only; fix the effort per model) + `agent-preamble.md` + `---` + the template's rules block up to the first `{{slot}}` + the tool list. A test hashes the rendered prefix for two lanes of the same kind and asserts equality.
- **System vs user placement.** Preamble and rules in the system message; packet, spec, tool results in user/tool turns. A change inside the system message zeroed the cache in 3/3 samples; user-side changes kept partial hits in 4/7.
- **Schema placement.** The schema is the `submit_answer` tool's `parameters` (constant bytes, part of the prefix), never pasted into the prompt. `required` lists every field a runner reads: STAGE_RESULT_SCHEMA gains `files_written`, `test_exit_code`, `read_witness`; REFLECT and SKEPTIC gain `read_witness`.
- **Context budgets per call** (qwopus9b, ~0.8 s per uncached kilotoken; double on qwen38): judges 6k prompt / 400 out; writers 12k / 1500; review lenses 16k with the diff chunked by file; tool results truncated head+tail at 4k chars (`_truncate_tool_output`); over budget is `local_prompt_over_budget`, never a silent cut.
- **Reasoning.** qwopus9b `enable_thinking: false` everywhere; if thinking is ever on, `max_tokens ≥ 512`. qwen38 `none` for judges, `low` for writers, `high` never. qwen: nothing to set; thinking needs the `qwen-think` alias.
- **Sampling.** Judges temperature 0.2; writers 0.6 with the launch flags' top_k 20 / top_p 0.95 (the server does not read generation_config).
- **Messages, not prompt strings.** Retire the REASONING/FILE/NEXT protocol and the think+decide double call in `agent_loop.py` (two requests per step on one slot, no continuation caching); keep the assistant `tool_calls` message verbatim so each turn is a byte-exact continuation.

## 7. KV cache design: level 1 and level 2 (slot save/restore)

**Level 1 (automatic, verified on all three models):** a byte-identical prompt reuses the slot's KV (411/415) and survives an intervening different prefix (411/415 again after a 31-token request, on qwen38, qwopus9b and qwen); a conversation continuation reuses everything before the new turn (776/810, 843/901). This is what datum gets for free by keeping prefixes byte-stable and histories verbatim, and it covers every call after the first of a stage kind while the model stays resident.

**Level 2 (explicit):** `POST /slots/<id>?action=save|restore` with `{"filename": "<name>.bin"}` on the model's internal port (read from `/running`'s `proxy`; not proxied on :8080), files under `/opt/kv-cache`; arcPI's `scripts/slot-cache.sh save|restore|list <model> <name>` does the port lookup and SSH. Not exercised here (state-changing on a shared box). How datum should use it:

- **What to save:** one slot state per (model, stage kind) taken right after a warm-up request whose prompt is exactly the stage's prefix and nothing else (system message + tool list, an empty or fixed user turn, `max_tokens: 1`). A save captures the whole slot, so warm with the prefix only, never with a real lane's packet.
- **Cache name:** `datum-<model>-<stage>-<sha12 of the rendered prefix bytes>.bin`; the sha is the same hash the prefix-stability test computes, so a template edit, a preamble regeneration by `datum awake`, a tool-list change or a different reasoning setting is a new name, and a stale file is never restored over a different prefix.
- **What the prefix must never contain:** anything per run or per lane: run id, the batch `inputs fingerprint` line (that belongs to hosted batch prompts, not local stage prompts), worktree paths, task ids, timestamps, the packet, the lane spec, PROPERTIES.md, a per-episode salt (`agent_loop.py`'s `<project-rules-<salt>>` tag would defeat it), and on qwen38 a varying `reasoning_effort`. All of those go after the prefix, in the user turn.
- **When restore pays:** only for the first request after the slot no longer holds the prefix and the host prompt cache does not either: a server restart, a main-group swap, or eviction by enough other traffic (host cache size **unverified**). Recompute cost is the prefix's prefill: a 2k-token stage prefix is ~1.7 s on qwopus9b and ~3.6 s on qwen38; a restore over SSH with a port lookup costs about that much. Level 2 therefore pays on qwen38 for prefixes ≥ ~5k tokens (preamble + rules + PROPERTIES.md relay) and barely at all on qwopus9b, where level 1 plus a 2 s recompute is simpler and cannot restore a stale state by mistake.
- **Mechanics:** save/restore only under the same flock as requests (a save during processing is refused); `restore` then the real request is a plain continuation, so `cached_tokens` on that request is the acceptance check (≥ 90% of the prefix tokens); log `local_slot_restore: <name> cached=<n>/<prompt>` and fall through to recompute on any error.
- **Recommendation:** build level 1 discipline (tasks 6 and 7) and log `cached_tokens`; add level 2 only if the benchmark shows cold-prefix time on the first call per stage kind above ~5% of lane wall-clock, which at qwopus9b's rates it will not.

Conclusions and per-stage guidance:

- **headroom does not shrink code**, which is what "read the lane's files" means, and its text compression drops whole records, so a test log through it can lose the failing assertion or the `TEST_EXIT=` line. Under the local stack headroom is off by default for code, for the lane spec and PROPERTIES relay (a byte-verified witness cannot survive a lossy pass), and for test output; the deterministic head+tail truncation at 4k chars is the safer bound. The one defensible use is a large, non-verdict tool output (a long `git log`, a directory listing) where the model may `headroom_retrieve` by keyword; even there it must be a separate tool result, never the relay. #516's "headroom on by default under the local runtime" should be inverted.
- **tokensave is the real lever for reads** (66–84% smaller views), but only with a graph indexed for the checkout the agent is reading: bare-name lookups on a stale index returned wrong bytes silently, which for a GREEN agent means implementing against the wrong function. Precondition: an index refresh per lane worktree as a batch step at lane intake (the CLI form is **unverified** here; the SQLite graph at `.tokensave/tokensave.db` is the no-MCP fallback), and lookups by qualified name (`<file>::<symbol>`).
- **Reaching the servers:** both are MCP servers attached to the Claude Code session. A `datum local-stage` process (mechanism A) can reach tokensave through its database or CLI, and headroom not at all unless datum embeds an MCP client; under mechanism B the host would expose them as tools. This is why the preamble's hedge ("when available") stays and why the local stage's tool list is datum's own.
- **Per stage:** writers (RED/GREEN/REFACTOR/structural) orient with `tokensave_read` map/signatures (~0.7–1.1k tokens per file instead of 4–5k), fetch the symbols they touch with `tokensave_body` by qualified name, and do a full `Read` only of the file they will write (a write needs complete bytes); budget ≤ 3 full reads and ≤ 8 bodies per stage, which keeps a writer's context within the 12k budget of §6. Judges (reflect, skeptic lenses, refactor-check) use `tokensave_body` for the functions under test and line-range reads of the test files, with no full-file reads; review lenses use `tokensave_affected`/`diff_context` for the epic diff instead of the whole diff. Batch runners use neither.
