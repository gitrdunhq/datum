## Refine — 2026-09-07

### Q1: [Architecture] What is the decision criterion for `.datum/state.json`'s fate — drop entirely, keep as archival-only, or keep as a live write-through cache?
> The TICKET names two candidate outcomes (drop entirely, or keep only as a one-shot archival export written at run-archive time) but gives no principle for choosing between them. This decision gates SPEC Requirement 8 (`state.json` fate) and Requirement 3 (`migrate.py`'s fate, since its entire purpose is schema-migrating `state.json`) — nothing in those requirements can be implemented until this is answered. I'm assuming the decision should be made on the basis of whether any consumer still needs a plain-JSON file outside the `datum` Python package (e.g. `datum-tui/data.py`, which explicitly avoids importing `datum`) — is that the right criterion, or is there a different one (e.g. performance, external tooling, migration risk)?

[Answer]: Drop the live write-through cache. `.datum/state.json` survives only as a point-in-time export written at archive time (`.datum/runs/<run_id>/state.json`, the rollback/archive/closeout snapshot the TICKET already carves out). Criterion: no consumer needs a live JSON mirror; the one out-of-package reader, `datum-tui/data.py`, reads `.datum/state.db` read-only through the stdlib `sqlite3` module, which keeps its no-`datum`-import property. `migrate.py` becomes the one-shot importer of a legacy `state.json` into `state.db` and is otherwise retired.

### Q2: [Architecture] Should `load_state()`/`save_state()`/`update_state()` be redesigned as part of this work, or adopted unchanged as the canonical accessor?
> Codebase scan found these 3 functions currently have zero production callers — only tests and a docstring-check template import them. Designating unused code as the canonical contract for 12+ consumers without revisiting its shape (return type, validation, error handling) carries risk that gaps only surface once real callers land. I'm assuming they can be adopted as-is (SPEC Assumption #1) — is that right, or should the contract be redesigned/hardened first?

[Answer]: Adopt `load_state()`/`save_state()`/`update_state()` unchanged as the contract. Harden only where a migrated module's tests surface a concrete gap (a missing key default, an error type a caller depends on), each hardening under its own test; no redesign of shape, return types or error handling ahead of a real caller.

### Q3: [Scope] Should migration onto the canonical accessor be an atomic flag-day cutover across all 12 modules, or incremental module-by-module, and if incremental, in what order?
> This determines whether each of the 7 independent-implementation modules and 3 bare-Path readers (SPEC Requirements 2 and 4) can ship as separate, independently reviewable and revertible changes, or must land in one combined change. I'm assuming incremental, module-by-module migration is acceptable and that no circular dependency between these 12 modules and `datum/state.py` blocks that ordering (SPEC Assumption #3) — is that right, and if incremental, is there a required order (e.g. modules with existing test coverage first, like `pr_comment_monitor.py`)?

[Answer]: Incremental, one module per lane, each independently reviewable and revertible. Order: modules with existing tests first (`pr_comment_monitor.py`, `status_render.py`), then `spec_drift_detector.py`, `rollback.py`, `no_diff_guard.py`, `path_utils.py`, then the bare readers (`report_bug.py`, `archive.py`, `datum-tui/data.py`), and pipeline-critical `pipeline_scheduler.py` last with tests written before it changes. No circular dependency with `datum/state.py` is known; a lane that finds one stops and reports it rather than working around it.

### Q4: [Behavior] If a module cannot cleanly migrate onto the canonical accessor (e.g. `corpus_sql.py`'s need for SQL-queryable access, `migrate.py`'s schema-migration purpose), is a documented, permanent fallback to direct reads acceptable, or must every one of the 12 modules end on the canonical accessor with zero exceptions?
> SPEC Requirements 3 and 5 currently model `migrate.py` and `datum/memory/corpus_sql.py` as permitted, documented exceptions rather than forced migrations, on the same reasoning as the already-accepted `rollback.py`/`archive.py` archival-export carve-out. I'm assuming documented exceptions are acceptable when a module has a genuine structural reason (not just convenience) — is that right, or must this epic be all-or-nothing across all 12 modules?

[Answer]: Documented exceptions are acceptable only for a structural reason, and only two: `datum/memory/corpus_sql.py` may keep its read-only `ATTACH` of `state.db` (it reads the canonical store, not the JSON cache; its `state.json` DuckDB view goes), and `migrate.py` may read a legacy `state.json` once as the importer. Every other module ends on the canonical accessor; no direct `state.json` read or write survives outside the archive export.

### Q5: [NFR] Should `state.db`'s schema (the `kv_state` table shape, key naming convention) be versioned and documented before this consolidation proceeds, to prevent the same kind of silent divergence recurring at the schema level?
> No architectural principle was given in the TICKET for this, and codebase scan did not find existing schema documentation for `state.db`. Without an answer, this epic's scope stays limited to unifying the accessor functions themselves, with no explicit schema-versioning deliverable. Should schema documentation/versioning be added as an in-scope requirement of this epic, or is it a separate follow-up?

[Answer]: In scope, minimal: a `SCHEMA_VERSION` constant in `datum/state.py`, stored in the db, plus a docstring table of the `kv_state` keys and their owners. No migration framework; a future schema change bumps the constant and the importer handles it.

### Q6: [NFR] Does the canonical accessor need new locking/transaction semantics beyond `update_state()`'s existing sqlite `EXCLUSIVE` transaction, or is SQLite's default isolation sufficient once all 12 modules route through it?
> A peer audit agent (`concurrent-write-race-sweep`) is active in this same session specifically looking for concurrent-write races. Codebase scan confirmed `update_state()` already wraps its read-modify-write in an `EXCLUSIVE` sqlite transaction, and found no evidence of a multi-process concurrent-write scenario beyond what that isolation already serializes. I'm assuming the existing `EXCLUSIVE` transaction is sufficient and no new locking is needed (SPEC Assumption #8) — is that right, or does consolidating 12 modules onto one accessor change the concurrency profile enough to need more (e.g. a file lock, a retry-on-busy policy)?

[Answer]: The existing `EXCLUSIVE` transaction in `update_state()` is sufficient; add a `busy_timeout` (5 s) on every connection so a concurrent reader retries instead of failing on SQLITE_BUSY. No file lock, no new transaction layer.

### Q7: [Behavior] What test evidence is required to certify "backwards compatible" across the 12+ migrated modules — per-module unit tests only, or a cross-module integration/contract test?
> No integration test spanning all 12 target modules exists today per codebase scan. SPEC Requirement 10 currently proposes per-module unit tests (e.g. new `tests/test_pipeline_scheduler.py`, `tests/test_rollback.py`) as the verification bar. Is that sufficient, or is an end-to-end test needed that writes state once via the canonical accessor and confirms every migrated module reads the expected values back? The answer changes how much new test-writing this epic's scope includes, and what error modes (e.g. a module silently falling back to stale/empty state) count as acceptable versus a hard failure.

[Answer]: Both. Per-module unit tests for each migrated module, and one contract test that writes state once through the canonical accessor and reads it back through every migrated module's public read path. A module that silently reads empty or stale state is a hard failure; a missing db must raise a named error from the accessor, never return `{}`.
