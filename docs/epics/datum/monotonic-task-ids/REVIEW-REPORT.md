| SEC-001 | **medium** | datum/task_ids.py | 59 | resolve_task_id_prefix() returns a config-supplied `task_id_prefix` (from `.datum/config.json`) completely unvalidated: `existing = config.get("task_id_prefix"); if existing: return existing`. Only the *derived* fallback path (_derive_prefix, lines 41-49) enforces a shape (>=2 letters, uppercase-only). This prefix seeds every generated lane/task id via `f"{prefix}-{counter}"` in datum/task_renumber.py's renumber_tasks() and is consumed by lane_plan.py's --renumber CLI path (lane_plan.py:840-857) before any schema check runs against it. PROPERTIES.md's own SECURITY-001 states the design intent for this epic: 'lane-steps.ts's completionMarkerCommand/laneSpecExportCommand reject any task id containing a shell metacharacter (an id isLaneId rejects) rather than passing it into a constructed shell command' — i.e. ids are expected to be validated at construction, not caught later. Here the opposite happens: an operator- or repo-supplied prefix containing shell metacharacters, spaces, or other unexpected bytes is accepted verbatim and only ever gets rejected indirectly, if and when a later JSON-schema check (validate_json_schema against $defs.laneId.pattern in lane_plan.py:870) happens to run before the resulting ids reach a shell-command consumer such as skills/src/shared/lane-steps.ts's setupSteps(), which interpolates lane ids unquoted into a bash command (`--lane-ids ${o.laneIds.join(',')}`, lane-steps.ts:784, pre-existing/untouched by this diff but now fed by a wider space of possible id shapes than the old digit-only task-N ids).
