# Workflow runner core: run datum bundles outside Claude Code

## What

datum's workflow bundles (`skills/datum-*.js`) run only inside Claude Code's Workflow tool, which supplies the sandbox globals (`agent`, `parallel`, `pipeline`, `phase`, `log`, `workflow`, `args`, `budget`) and has no shell, so every shell command is wrapped in an LLM call (the `datum-cli` batch runner). This epic adds a host-side runner that executes the same bundles unchanged, runs `datum-cli` batches as real subprocesses, routes every other `agent()` call through a pluggable stage executor behind per-model concurrency limits, records per-call metrics, and validates stage replies against their schema. It is the core of the design in the homelab repo `docs/plans/datum-on-pi.md` (slices 1, 2, 3 and 8); the pi stage executor, role prompts, external commits, launcher, tracker and interview are later epics.

## Requirements

1. **Shell seam in `runBatch`.** `skills/src/shared/sandbox.d.ts` declares an optional global `shell(script: string, opts: { cwd: string; timeoutMs: number }): Promise<{ exit_code: number; stdout: string; stderr: string }>`. `runBatch` (`skills/src/shared/agents.ts`) accepts `deps.shell` and falls back to `globalThis.shell`; when either is defined it runs `batchScript(steps)` through it with the batch root as `cwd` and `BATCH_TOOL_TIMEOUT_MS` as the timeout, parses the stdout with the existing `parseBatchResult`, and never calls `agentFn`. When neither is defined, behaviour is byte-for-byte what it is today (the Claude Code path is unchanged). A `shell` that throws or returns a non-zero exit with unparseable stdout yields `missing: true` with `scriptError` naming the cause.
2. **Every `datum-cli` call goes through `runBatch`.** The direct `agent(batchCommandPrompt(...))` callers (`verifyCommitIndependently` in `agents.ts`, dep-merge in `datum-tdd-act-lane.ts`, and any other caller found by `grep -rn batchCommandPrompt skills/src --include=*.ts`) are moved onto `runBatch`. After the change, `batchCommandPrompt` is referenced outside tests only in `shared/batch.ts` and `shared/agents.ts`.
3. **Runner module.** `skills/src/runtime/runner.ts` exports `runBundle(opts: { bundlePath: string; args: unknown; executor: StageExecutor; shell: ShellFn; skillsDirs: string[]; log: (line: string) => void }): Promise<unknown>`. It reads the bundle, wraps its body in an async function so the top-level `return` works and `export const meta` is kept as a value, and supplies every global in `sandbox.d.ts`: `parallel` runs thunks concurrently and maps a rejection to `null` (as the Workflow harness does); `pipeline` runs items through the stages in order; `phase` and `log` call the log function; `budget.total` is `null` and `spent()` is the sum of recorded tokens; `workflow({ scriptPath })` and `workflow({ name })` load the nested bundle from `skillsDirs` (`.datum/skills` first, then the configured `skills_dir`) and run it with the same executor and shell. `Math.random` inside a bundle is not patched (the bundles already avoid it).
4. **Stage executor interface.** `skills/src/runtime/executor.ts` defines `interface StageExecutor { execute(req: StageRequest): Promise<StageReply> }` where `StageRequest` is `{ prompt, opts: AgentOpts, model: string, headers: Record<string, string> }` and `StageReply` is `{ text: string; usage?: { prompt_tokens, completion_tokens, cached_tokens }; timings?: { prefill_ms, decode_ms } }`. The runner's `agent()` builds the request from `opts` and the runtime config, sends it through the semaphore (R6), parses the reply with `parseAgentJson`, and validates it (R8). An `agent()` call whose `opts.agentType` is `datum-cli` is rejected by name (`cli_call_bypassed_runbatch`) instead of reaching the executor.
5. **Fake executor for tests.** `skills/src/runtime/fake-executor.ts` answers from a script keyed by `opts.label` prefix (first match wins, then a default), records every request with start and end timestamps, and can hold a request open until the test releases it, so concurrency can be asserted. It is the only executor this epic ships; no HTTP client is written here.
6. **Runtime config, tiers and concurrency.** `.datum/config.json` gains a `runtime` block read by `readRuntimeConfig()` in `skills/src/shared/models.ts`: `kind` (`"fake"` or `"pi"`; unknown is a named error), `models` (`{ fast, balanced, deep }` model ids, fed to `setModelTiers`), `concurrency` (`{ [modelId]: n }`, default 1 for any model not listed), `priority` (default `"batch"`) and `client` (default `"datum"`). The runner keeps one semaphore per model id; at no time are more than `concurrency[model]` requests in flight for that model; waiting requests are served FIFO within a model, and when several are waiting the one whose `agentType` matches the request that just finished goes first (kind grouping, for prefix-cache locality). Every request carries headers `X-Client: <client>` and `X-Priority: <priority>`.
7. **Per-call metrics.** Every executed request appends one JSON line to `<repoRoot>/.datum/runs/<runId>/metrics.jsonl` with `ts, run_id, label, agent_type, model, prompt_tokens, completion_tokens, cached_tokens, prefill_ms, decode_ms, queue_wait_ms, wall_ms, attempt, outcome` (`ok`, `invalid`, `error`); `runId` comes from `args.runId` when present, else from the runner's start time. `datum closeout-collect-token-metrics` (or the existing collector it extends) reads that file and returns per-stage totals and the cached share per agent type; a missing file is an empty result, not an error.
8. **Stage output contract.** `STAGE_RESULT_SCHEMA` in `skills/src/shared/schemas.ts` lists `files_written`, `test_exit_code` and `read_witness` as required; `REFLECT_SCHEMA` and `SKEPTIC_SCHEMA` list `read_witness` as required. The runner validates each parsed reply against `opts.schema` when one is given (required keys present, declared types match); an invalid reply is logged as `stage_output_invalid: <label>: <missing or wrong fields>` and retried exactly once on the next tier up (`fast` to `balanced`, `balanced` to `deep`; a `deep` miss is not retried), never on the same model; a second miss returns `null`. The hosted Claude Code path is unaffected by the stricter `required` lists because `assertReadWitness` already demands those fields.
9. **CLI entry.** `datum workflow run <name> --args <file> [--config <path>]` in `datum/cli.py` spawns `node` on the compiled runner (`skills/runtime/runner.js`, built by `scripts/build-workflows.sh` as a second esbuild target, not a workflow bundle, with the same `@generated` banner) with the bundle resolved from `.datum/skills/<name>.js` then `skills_dir`, the args file's JSON, and the runtime config; it prints the bundle's result as JSON on stdout and exits 0 on a result, 1 on a thrown error (message on stderr), 2 on usage errors (missing bundle, unparseable args, unknown `runtime.kind`).
10. **End-to-end fixture.** `skills/src/runtime/fixtures/fixture-go.js` and `fixture-child.js` are two small bundles in the real post-processed shape (hoisted `export const meta`, top-level `return`) that between them call `phase`, `log`, `agent` with and without a schema, `parallel` with one rejecting thunk, `runBatch`-shaped shell work through a real `shell`, and `workflow({ name })`. A vitest proves `runBundle` returns the parent's result with the child's result embedded, the shell step ran as a subprocess (its stdout appears in the result), the rejected thunk is `null`, the fake executor saw exactly the expected requests in order, and `metrics.jsonl` has one line per request.

## Not This

- No pi stage executor, no `tools/pi/stage.sh`, no lane-guard extension (homelab repo, slices 4 and 5).
- No HTTP or OpenAI-compatible client; the only executor is the fake. The real executor arrives with the pi stage work.
- No role prompt materialisation, no `lane-guard.json` writer (slice 6); no external-commit path in the lane script (slice 7); no `datum doctor --runtime pi` (slice 10); no `datum go` launcher, entry detection or halt handling (slice 12); no Plane tracker (slice 14); no ticket interview (slice 15).
- No change to how the bundles behave under the Claude Code Workflow tool: with no `shell` global and no runtime block, every call site does exactly what it does today.
- No changes to `datum/local_llm.py` or `datum/agent_loop.py`.
- No replay cache keyed by prompt (slice 13).
- No new runtime dependencies in `package.json` or `pyproject.toml`; Node 22 and the existing esbuild, vitest and typer are enough.

## Decisions

- The runner lives in the datum repo under `skills/src/runtime/` and is reachable only through `datum workflow run` (datum's CLI rule).
- `datum-cli` work bypasses the model entirely when a `shell` is present. Any `datum-cli` call that still reaches `agent()` is a bug and fails by name rather than silently costing a model call.
- Concurrency is a per-model semaphore inside the runner, not a change to lane scheduling; `pipeline.max_concurrent` keeps its meaning.
- Stricter `required` lists apply to both runtimes. The hosted agents already return those fields, and a schema that leaves them optional is how local models drop them.
- Tests for TypeScript lanes run with `npx vitest run <file>`; tests for Python lanes run with `uv run pytest -x -q <file>`. The repo default `test_command` is pytest, so the plan sets a per-lane `test_command` for TypeScript lanes.
- The pre-existing vitest failure "under real zsh" in `batch.test.ts` is an environment gap (no zsh on this host), not part of this epic.
