<result>## Report: FluidAudio Diarization Tuning — Issue #306

### Part 1 — Built-in DER/purity scoring (YES, it exists)

**`DiarizationDER`** (`Sources/FluidAudio/Diarizer/DiarizationDER.swift`) is a **public** API in the main `FluidAudio` library target — directly importable by `Tools/ProofHarness` today, no new dependency needed. It implements the standard pyannote/NIST md-eval DER formula (miss + false-alarm + confusion, Hungarian-matched hyp→ref mapping, configurable collar). Input type is `DERSpeakerSegment(speaker:start:end:)`; output is `DERResult(der:confusion:falseAlarm:miss:totalRefSpeech:mapping:)` — the `mapping` field is exactly the cluster-purity signal issue #306 needs (which hyp cluster the Hungarian solver assigned to which true speaker, and which hyp clusters got no match = pure over-segmentation).

A richer, segment-overlap-based version — `DiarizationMetricsCalculator.offlineMetrics()` in `Sources/FluidAudioCLI/Utils/DiarizationMetrics.swift` — adds JER and per-rate breakdowns (missRate/falseAlarmRate/speakerErrorRate), but it's **internal to the `FluidAudioCLI` executable target**, not exported from the library, so it can't be imported directly — porting the ~150-line algorithm (or copying the file) would be needed to use it.

**Wiring plan**: `ProofHarness` already has `FluidDiarizationPlugin` output as `[SpeakerSegment]`; map those + parsed `.rttm` ground truth into `[DERSpeakerSegment]` and call `DiarizationDER.compute(ref:hyp:)` directly. One gap: FluidAudio's RTTM parser (`RTTMParser.loadSegments`) also lives only in `FluidAudioCLI`, not the library — ProofHarness needs its own trivial RTTM line parser (~15 lines) or a copy of that file.

### Part 2 — Upstream config knobs + precedent

Repo: `https://github.com/FluidInference/FluidAudio` (pinned rev `8048812...`, v0.14.7 per `Package.resolved`).

Found the exact tunable in `OfflineDiarizerTypes.swift`: `OfflineDiarizerConfig.Clustering`:
```swift
public static let community = Clustering(
    threshold: 0.6,       // Euclidean distance on unit-normalized embeddings
    warmStartFa: 0.07, warmStartFb: 0.8,
    minSpeakers: nil, maxSpeakers: nil, numSpeakers: nil
)
```
`minSpeakers`/`maxSpeakers`/`numSpeakers` are direct config overrides on the same struct — since our fixtures have known ground truth (4 speakers), setting `maxSpeakers: 4` (or `numSpeakers: 4`) is a zero-risk immediate mitigation for the fixture benchmark, independent of threshold tuning.

**Direct upstream precedent for our exact symptom**: FluidAudio's own benchmark docs/tables show mismatched-threshold over-segmentation on AMI meetings that mirrors #306's ratio almost exactly — e.g. `ES2004a: 7 predicted vs 4 actual`, `IS1002b: 9 predicted vs 4 actual`. Upstream guidance: **lower threshold → more/smaller clusters (over-segmentation)**, **higher threshold → fewer/merged clusters**. Default `0.6` targets ~18–20% DER on AMI-SDM (offline/VBx pipeline); an older non-VBx pipeline used `0.7` for ~17.7% DER. Given our 8-vs-4 result, the first experiment to run is raising `threshold` from `0.6` toward `0.7`–`0.8` on `meeting-15min.wav`, in combination with (or instead of) an explicit `maxSpeakers` cap.
