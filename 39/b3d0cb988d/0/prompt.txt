## Flex Tier / Batch Processing for Claude Code Workflows -- Research Findings

### 1. What is "Flex" Processing?

**"Flex" does not exist on the Anthropic API.** It is an AWS Bedrock-only concept. What Anthropic offers directly is three tiers:

| Tier | Description |
|------|-------------|
| **Priority** | Production workloads needing guaranteed availability |
| **Standard** | Default for all API requests (best-effort) |
| **Batch** | Asynchronous processing via Message Batches API, **50% discount** |

The **Message Batches API** (`POST /v1/messages/batches`) is the cost-reduction path. It accepts up to 100,000 requests per batch (or 256 MB), processes them asynchronously (most complete in under 1 hour, max 24-hour SLA), and results are available for 29 days.

**If you use Claude via AWS Bedrock**, there IS a `service_tier: "flex"` option that provides ~50% discount with relaxed latency -- but that is a Bedrock feature, not Anthropic direct API.

### 2. How to Opt In

**Anthropic API (direct):**
- The Messages API `service_tier` parameter only accepts `"auto"` (default) and `"standard_only"`. There is **no** `service_tier: "flex"` or `"batch"` value.
- To get the 50% discount, you must use the **separate** Message Batches endpoint: `POST /v1/messages/batches`.

**AWS Bedrock:**
- Claude Code v2.1.122+ supports `ANTHROPIC_BEDROCK_SERVICE_TIER` environment variable with values: `default`, `flex`, `priority`.

### 3. Claude Code Integration

**Claude Code does NOT support service tier selection for the Anthropic API.** Confirmed absent:
- No CLI flag for service tier
- No `settings.json` key
- No `ANTHROPIC_SERVICE_TIER` or `CLAUDE_SERVICE_TIER` environment variable
- The `agent()` function accepts: `label`, `phase`, `model`, `schema` -- **no `service_tier` parameter**
- No way to route Claude Code requests through the Batches API

**The only exception:** `ANTHROPIC_BEDROCK_SERVICE_TIER` for Bedrock deployments.

### 4. Scheduling Considerations

**Batch API pricing is always 50% off** -- there is no time-of-day variation. The discount is structural, not temporal. Rate limits for batches are separate from the Messages API (HTTP request limits and queue depth limits apply independently).

### 5. Batch API vs Flex Tier

| Feature | Batch API (Anthropic) | Flex (Bedrock only) |
|---------|----------------------|-------------------|
| Access | `POST /v1/messages/batches` | `service_tier: "flex"` on Bedrock InvokeModel |
| Discount | 50% | ~50% |
| Latency | Async, up to 24h SLA | Synchronous but deprioritized |
| Integration | Separate endpoint, poll for results | Drop-in parameter on existing calls |
| Claude Code support | None | `ANTHROPIC_BEDROCK_SERVICE_TIER=flex` |

These are **different mechanisms**. Batch is Anthropic's own async queue. Flex is Bedrock's deprioritized inference.

### 6. Practical Architecture for Your Pipeline

**Option A: Bedrock + Flex (simplest integration)**

- AWS Bedrock access configured for Claude models
- Claude Code v2.1.122+
- All `agent()` calls automatically use flex tier -- no code changes needed
- Synchronous execution preserved (your DAG scheduling still works)
- Trade-off: Bedrock adds its own markup on top of model pricing

**Option B: Direct Batch API (maximum savings, requires rearchitecture)**
Replace `agent()` calls with direct Anthropic SDK batch submissions:

```python
# Poll until complete

    batch = client.messages.batches.retrieve(batch.id)
    time.sleep(30)

for result in client.messages.batches.results(batch.id):
```

## GitHub Sub-Issues: Complete API Reference

### 1. Sub-Issues API -- Confirmed Working

Sub-issues are a **public preview feature** (launched January 2025). Both REST and GraphQL APIs are live and functional -- I verified against your `gitrdunhq/datum` repo.

#### REST API

All endpoints work with the standard API version (`2022-11-28`) -- no special preview header required for REST.

| Operation | Method | Endpoint |
|-----------|--------|----------|
| List sub-issues | `GET` | `/repos/{owner}/{repo}/issues/{issue_number}/sub_issues` |
| Get parent | `GET` | `/repos/{owner}/{repo}/issues/{issue_number}/parent` |
| Add sub-issue | `POST` | `/repos/{owner}/{repo}/issues/{issue_number}/sub_issues` |
| Remove sub-issue | `DELETE` | `/repos/{owner}/{repo}/issues/{issue_number}/sub_issue` |
| Reprioritize | `PATCH` | `/repos/{owner}/{repo}/issues/{issue_number}/sub_issues/priority` |

REST `POST` body uses the **numeric issue ID** (not issue number, not node_id):
```json
{ "sub_issue_id": 4657937828 }
```

Example `gh` CLI call to add a sub-issue:
```bash
unset GITHUB_TOKEN &amp;&amp; gh api -X POST repos/gitrdunhq/datum/issues/100/sub_issues -f sub_issue_id=4657937828
```

#### GraphQL API

Requires the header `GraphQL-Features: sub_issues` for queries. Three mutations confirmed in the schema:

**`addSubIssue`** -- Input: `issueId` (required, node_id), `subIssueId` (optional, node_id), `subIssueUrl` (optional, string URL), `replaceParent` (optional, boolean). You can use **either** `subIssueId` or `subIssueUrl` -- the URL option is simpler since you don't need to look up node IDs.

```bash
unset GITHUB_TOKEN &amp;&amp; gh api graphql -H "GraphQL-Features: sub_issues" -f query='
  mutation {
    addSubIssue(input: {
      issueId: "I_kwDOSkfrNM8AAAABPARENTID"
      subIssueId: "I_kwDOSkfrNM8AAAAABCHILDID"
    }) {
      issue { number title }
      subIssue { number title }
    }
  }
'
```

**`removeSubIssue`** -- Input: `issueId` (required), `subIssueId` (required). Both are node_ids.

**`reprioritizeSubIssue`** -- Input: `issueId` (required), `subIssueId` (required), `afterId` or `beforeId` (one required).

### 4. Issue Body as Structured Data

There is no GitHub convention for this, but HTML comments are the standard workaround since they're invisible in rendered markdown but machine-parseable:

```markdown
## Epic: Feature X

Human-readable description here.

### Tasks
- [ ] Task 1 (#201)
- [ ] Task 2 (#202)

&lt;!-- datum:metadata
epic_id: feat-x
files: [src/foo.py, tests/test_foo.py]
depends_on: [201, 202]
acceptance_criteria:
  - foo() returns 42
  - bar() handles null input
--&gt;
```

This approach is solid because:
- HTML comments are preserved in the raw body but invisible in rendered view
- Parseable with a simple regex: `&lt;!-- datum:metadata\n(.*?)\n--&gt;` then YAML parse the contents
- Survives GitHub's markdown rendering pipeline
- Won't confuse humans reading the issue
- Easy to update via `gh issue edit --body`
