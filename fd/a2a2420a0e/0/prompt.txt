## Adversarial Review: Resume/Crash Safety in `datum-tdd-act.js`

### BUG 1: DAG Deadlock on Resume (CRITICAL)

**Lines 688-728** — The DAG scheduler creates fresh `depPromises`/`depResolvers` maps on every run, including resume runs.

**The scenario**: Tasks A, B, C are in one batch. B depends on A. Crash happens after A completes but during B's GREEN stage. User resumes with `resumeFromRunId`.

On resume, the Workflow runtime replays cached `agent()` calls. Here is the problem:

1. `depPromises` and `depResolvers` are created fresh (lines 689-692) — they are runtime-only JavaScript objects, not persisted.
2. All tasks in the batch are launched via `parallel()` (line 696).
3. Task A's `runLane()` is called. Inside `runLane()`, all its `agent()` calls replay instantly from cache (skeleton, red, verify-red, reflect, green, verify-green, skeptics, refactor). Task A finishes in milliseconds.
4. Task A's result is passed to `depResolvers[taskA]()` at line 725 — this resolves task A's promise.
5. Task B was waiting on `depPromises[taskA]` at line 711. It resolves, B proceeds.

**Verdict: This specific path is SAFE.** The `parallel()` call re-runs the full DAG scheduling logic including the dep-wait. Even though A's agents replay from cache, A still calls `depResolvers[taskA](result)` at line 725, which unblocks B. The Promise machinery works correctly regardless of whether the agent calls inside `runLane()` are cache-replayed or fresh.

**BUT there is a subtle race**: If the Workflow runtime replays `runLane()` for task A entirely from cache *synchronously* (zero microtask ticks), then `depResolvers[taskA](result)` at line 725 fires *before* task B has reached its `await Promise.all(...)` at line 711. Since `Promise.resolve()` stores the resolved value and late `.then()` callers receive it immediately, this is still safe in JavaScript's Promise semantics.

**No deadlock here.** The design is sound for this case.
